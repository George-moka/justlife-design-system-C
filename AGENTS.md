# AGENTS.md — Justlife Design System

Operating rules for **anyone (or any AI tool) building in this repo** — Claude Code, Cursor, Copilot,
a teammate, whoever. Tool-agnostic on purpose. **Read this before creating or changing anything.**

- Formal policy & approval flow → [`docs/governance.md`](docs/governance.md)
- Day-to-day commands & setup → [`docs/contributing.md`](docs/contributing.md)
- Cross-platform (RN / RNW) rules → [`docs/platform-rules.md`](docs/platform-rules.md)
- Current build state / where to resume → [`docs/HANDOFF.md`](docs/HANDOFF.md)

This is a **code-first** design system: code is the source of truth, Figma is reference. Mobile-first
(React Native + react-native-web), every visual value comes from `@justlife/tokens`.

---

## The three non-negotiables

1. **Reuse before creation.** Audit existing components → patterns → tokens → variants before adding
   anything new. The smallest addition that fits the system wins.
2. **Tokens only.** No raw colours or dimensions in component/pattern code — ever. Use `useTheme()`.
3. **Everything is documented & tested.** Each component ships stories, MDX docs, and tests.

## Never invent — ask first

This is a **company** design system. Do **not** invent tokens, colours, assets, icons, or components
on your own. If something seems missing, surface it and ask. Adding a token is a **system-level
decision** (justify in the PR, place in the right tier, get CODEOWNERS approval — see governance).
The one historical carve-out (motion tokens) was explicitly authorised; treat it as the exception,
not the pattern.

---

## Design conventions

The accumulated, reusable rules. **Enforcement** says how the rule holds today — `Enforced` means a
token/default/lint/test makes it automatic; `Convention` means you must apply it by judgment (and it's
a candidate to graduate into code — see the ladder below).

> **This table is the living rulebook, fed by the user's design feedback.** Every critique — a high-level
> expectation or a small recurring preference — gets distilled into a row here (and pushed down the ladder
> into a token/component/lint where possible) so it's applied *automatically* next time, not repeated. When
> you get feedback, add or sharpen a rule before moving on.

| # | Rule | Why | Enforcement |
|---|------|-----|-------------|
| 1 | **Every visual value comes from a token** (`useTheme()` → `t.*`). No raw hex / rgb / dimension literals. | System integrity; theming. | **Enforced** — `justlife/no-raw-values` ESLint rule. |
| 2 | **Text uses Poppins via typography tokens** (`t.typography.*` / `<Text variant=…>`), never ad-hoc font sizes/weights. | One type system. | **Enforced** (colour/dimension lint) + Convention (variant choice). |
| 3 | **Defaults:** corner radius **12** (`radius.default`), horizontal spacing **8** (`space.default`), stroke **0.5** (`borderWidth.hairline`). | Consistency baseline. | **Enforced** — baked into token values. |
| 4 | **Off-scale spacing snaps to the nearest `space` step** (e.g. Figma 12→`sm`/8 region, 6→`xs`). Don't add a token for a one-off gap. | Avoid token proliferation. | Convention (lint blocks raw numbers; "snap" is judgment). |
| 5 | **Bottom-anchored bars clear the iOS home indicator** — `CheckoutBar` / `BottomNavigation` sit `safeArea.bottom` (34px) above the screen edge. Anchor the bar flush to `bottom: 0` and let the component supply the inset. | Matches iOS / Instagram; avoids clipping. | **Enforced** — `safeArea.bottom` token + component default. Convention when hand-placing a new bar. |
| 6 | **Keep a component's shape consistent across its states.** A state change must not alter geometry the user reads as "the same element" — e.g. the expanded `CheckoutBar` keeps the collapsed bar's bottom-corner curvature. | Avoids jarring transitions. | Convention (candidate: visual-regression test). |
| 7 | **`Button size="xs"` (~32px) is the DEFAULT everywhere — in cards AND screen-level states (Empty / Error / inline actions). Never `sm`/`md`/`lg` unless it's a deliberate full-width page / bottom-bar CTA.** The 22px `2xs` is only the Add-toggle that height-matches the QuantityStepper. `sm`/`md`/`lg` read as chubby against the compact type — don't argue tappability to justify them. **Before adding any Button, match the size to comparable existing usages (xs dominates), don't pick by feel.** | The user flags chubby buttons repeatedly — most recently the EmptyState/ErrorState Retry shipped at `sm` (the old rule's "screen-level" loophole). | Convention (lint candidate: warn on non-xs/2xs `Button` outside a full-width bar). |
| 8 | **Two selection treatments:** *chips/segments* → solid brand fill + `onBrand` text; *cards & `TabGroup`* → `#00C3FF` outline + `background.selected` light-blue fill. | One selected-state language. | Convention. |
| 9 | **Mobile-first.** Stories render in a 375px phone frame by default; full screens opt out with `layout: 'fullscreen'`. Screen demos must **fill the viewport** (absolute inset:0), not a fixed height, so bars reach the real device edge. | Real mobile sizing. | **Enforced** (preview decorator default) + Convention (fill-viewport for screens). |
| 10 | **Don't dress static info as interactive.** Solid-brand fills, button/pill shapes and "selected" styling are reserved for live, tappable choices. Informative values (a chosen plan, a summary field) are plain text — optionally a small icon or muted `Badge` — never a CTA-sized pill. | Affordance must match behaviour; avoids fake buttons. | Convention. |
| 11 | **Self-check every build:** corner radius, spacing, and font-size accuracy/consistency — before handing off, not after the user flags it. | Quality bar. | Convention (process). |
| 12 | **A page's top inset depends on its first item.** If the first item is a **card**, its top gap equals the page's left/right padding (`space.md`) so the inset reads even on all sides. If the first item is **text** (a heading/label), give it more room (`space.lg`) under the rounded card top. | Even framing for cards; breathing room for text. | Convention (`PageShell contentInsetTop`). |
| 13 | **Equal-size rows/items — HARD RULE.** Repeated rows in a table, list, or any "kinda design" with stacked items must all be the **same height** (fixed/`minHeight` + vertically-centred content), regardless of how much each one's text wraps. Never let one row be taller than its neighbours. | Rhythm; the user enforces this strictly. | Convention (set a shared row height). |
| 14 | **Reference/informational content stays neutral — don't colour to nudge.** A policy, fee schedule, or any read-only reference is plain neutral text — no green/amber/red severity coding that could read as steering a choice (e.g. a cancellation-fee table must not look like it's encouraging cancellation). Reserve tone colours for genuine status/feedback. Keep disclaimers/containers low-emphasis (`background.tertiary`), not loud tints. | Don't editorialise neutral info. | Convention. |
| 15 | **Consistent scroll — IMPORTANT RULE.** Every screen scrolls the same way: the **inner content area owns the scroll**, the page frame never rubber-bands. A screen whose content fits must stay put — not bounce the whole page — exactly like one whose content overflows and scrolls. Lock the document against the iOS overscroll bounce (`overscroll-behavior: none` on `html, body`, in `preview-head.html`); pinned screens scroll inside `PageShell`'s content `ScrollView`, never the body. | Pages felt different (short ones bounced the frame, long ones scrolled); the user flagged this as important. | **Enforced** — `overscroll-behavior: none` globally. |
| 16 | **Promote reusable atoms as you build — don't leave them inline.** When you compose a screen, any piece that's reusable (a chip, picker, card, section, callout) becomes a real `@justlife/ui` component (folder + `stories`/`docs`/`tests` + exported) **as part of that work**, not a local `function` in the screen. Screen-specific compositions (step bodies, sheet contents) stay inline — but say so explicitly. Don't ship a screen with reusable building blocks trapped inside it. | The DS is the source of truth; inline atoms are invisible, untested, and get duplicated. The user flagged the funnel's chips/pickers/cards being trapped in the screen while Profile's were promoted. | Convention (process). |
| 17 | **Spacing between items is always a `space.*` token via `gap` — never leftover space.** Don't use `justify="space-between"` to *create* gaps (those are leftover space, vary by screen width, aren't a token). To spread items across the width evenly, give them `flex: 1` and a token `gap`. | Every gap must be a real token (extends #4); the user flagged a weekday row whose inter-chip gaps weren't ours. | Convention (candidate: lint `space-between` used for spacing). |
| 18 | **Verify before you assert — read the code / rendered value, don't claim from memory.** Before stating a fact (a contrast ratio, which step something is on, "X is missing/broken/already there"), check it in the source or the running build. Flag judgment calls as conventions. | Wrong claims erode trust; in one pass I mis-stated a step number and an avatar-contrast "failure" that actually passed. | Convention (process). |
| 19 | **Text scales up, never down — a floor at the token size.** `Text` honours the OS Text-Size (Dynamic Type) setting **upward** (a user who needs bigger text gets it) but never renders **smaller** than its base token: scaling is off when the user's `fontScale` < 1, on at ≥ 1. Min-size is consistent on every phone; growth is the user's choice (uncapped — add `maxFontSizeMultiplier` only if a specific layout needs a ceiling). | A phone on a small Text-Size setting made the app look shrunken; a hard lock would hurt accessibility. | **Enforced** — default on the `Text` primitive (`allowFontScaling={fontScale >= 1}` via `useWindowDimensions`). |
| 20 | **Type-scale parity — font sizes are all odd (the user dislikes mixing odd & even).** The active text scale is **23 · 19 · 15 · 13 · 11 · 9** — every role is odd (moved off the even 24/20/16/14 → 23/19/15/13). **Never introduce an even text size.** | The user's stated preference — "if some fonts are odd and some even, I don't feel good." | **Enforced** — baked into the `font-size` scale → `typography` tokens (all active roles odd). |
| 21 | **All selectable chips share one *main-label* treatment.** Every `Selectable`-based chip — `PillGroup`, `TimeSlotPicker`, `NumberSelector`, `WeekdayPicker`, `DatePicker` — renders its **main label** identically: `labelBase` (13px semibold), `text.onBrand` when selected / `text.primary` when not. **Exception — captions:** a chip may add a small label *above* its main one (e.g. `DatePicker`'s weekday over the date number) — that's an intentional **`bodyMicro` (9px) / `text.secondary`** caption, deliberately smaller + muted. Keep the *main* label uniform across pickers; don't let it drift. | They're the same component (the user flagged a weekday chip drifted small/muted) — but the date's weekday is a caption the user wants smaller. | Convention (candidate: a shared chip-label helper). |

| 22 | **Lean light & airy — don't over-container.** Improve a screen through type **hierarchy, spacing, and selective accent** — *not* by wrapping simple form sections in white cards/boxes or padding them out with decorative strips. Reserve cards for genuine **content units** (product / plan / selectable cards — add-ons, frequency plans), never as containers for plain form fields (hours, pickers, yes-no). Empty space is fine; restraint over density. Don't add reassurance/trust elements that weren't asked for. | The user rejected a carded form step as "too boxy/heavy" and a trust strip as gimmicky; the brand reads clean and airy. | Convention. |

| 23 | **Emphasis scales to its surface — weight first, size only when standalone.** To emphasise a value (a total, a key figure), change **weight/colour**; step its **size** up *only* in a **standalone** surface (a titled card). Inside a **compact / `embedded`** surface (e.g. the `CheckoutBar` panel) keep the row's size and emphasise by **weight** alone — don't enlarge text in a tight space. | The user accepted the standalone checkout total going 11→13 semibold, but wanted the bottom-bar's embedded total back at 11, semibold only. | **Enforced** for `PriceDetails` (total `labelBase` standalone / `labelXSmall` embedded); Convention elsewhere. |

| 24 | **A reassurance / secondary block should recede — pale, tone-on-tone, single flat tones.** Style a "promise" / benefits block (e.g. "justlife Promise") to sit quietly *in* the paper: **no brand colour, no card / background, no emphasis**. Flat single tones in soft greys, paleness stepping **down** (point titles → heading → a faded seal icon). The seal is the faintest mark — the palest icon token + an `opacity` step. | The user wanted it "softer… 1 tone… softer than the heading," pressed into the paper; an earlier brand-glow "aurora card" was rejected. | Convention (Enforced in `PromiseList`). |
| 25 | **"Redesign" means recompose, not redecorate.** When the user asks to *redesign* something, change the **composition / layout** — don't just wrap the same arrangement in a background, card, or colour. Offer genuinely different structures and let them choose. | The user pushed back that adding a glow panel behind the same list wasn't a redesign. | Convention (process). |
| 26 | **Storybook-first → design WITH existing components → finalize → THEN bake.** Before designing **anything**, check the Storybook catalog for components that already exist; unless told otherwise, **build the design out of those** (reuse `PlanBookingCard`, `PageShell`, `Header`, … — never quietly invent a parallel or hand-roll a header). **Iterate / upgrade in-context until the design is 100% approved**; *only then* bake (commit) and update the components to the finalized design. Don't spin up new components / stories or promote to the catalog mid-iteration. This sets the **timing** for #16 (promote at finalization, not before approval). | The user: I built a parallel `BookingCard` + hand-rolled the Bookings header instead of reusing `PlanBookingCard` + `PageShell`, and started adding stories before the design was approved. | Convention (process). |
| 27 | **Status/state colours are a system — a "done" state recedes.** Map a flow's states to a consistent tone scheme and hold it: **ongoing / active** = `success` (green), **completed / done** = a **muted** tone (`info` light-blue, or `neutral`) — *not* `success`, so a finished item doesn't shout as loud as a live one — **cancelled** = `error` (red), **pending** = `warning`. Don't reuse one loud colour across unrelated states. And when you add a new affordance (e.g. a rate-input), **don't hide existing meaningful info** (e.g. the pro's own rating) — they coexist. | The user flagged Completed bookings rendered in the same green as Active, and a removed pro-rating badge. | Convention. |
| 28 | **Reward a peak action with subtle, contained delight — and *choreograph* the transition, don't cheap-fade it.** When a user completes a meaningful action, don't snap straight to the next control: insert a brief **confirmation** beat, then settle into the follow-up (e.g. "Book Again"). **A plain cross-fade reads as cheap** — animate the *actual elements*: e.g. the rated stars **gather onto one slot as the result text writes in beside them**. State the **outcome plainly** ("You gave 5 stars") — *not* the person's name. Reserve the *full* celebration — a `Confetti` burst (DS primitive, fired from the **card centre** so it rises clear of the footer — see #30, clipped to the card) + brand-colour copy — for the **peak** outcome only (a perfect 5★, *not* every rating). Use motion tokens; keep it **contained** (decorative, `pointerEvents:none`). Force the end-states via `setValue`/timers (not just the animation callback) so they hold even when a preview starves rAF. | The user wanted "some game" on the rating, banned the sparkle (#29), and rejected the first cross-fade as "very cheap" — asked to gather the stars onto the 5th slot with the text to its left, then transform to the button. | Convention (prototyped in `BookingsScreen` `RateableBookingCard` + DS `Confetti`). |
| 29 | **Never use the `sparkles` icon — or any glitter/✨ "sparkle" decoration.** The user finds it ugly. Don't reach for `sparkles` / `sparkle` / `wand-sparkles` as a celebratory or emphasis flourish; convey delight through **motion, colour, copy, or confetti** instead. (The rating `star` glyph for an actual rating is fine — this bans the decorative sparkle, not stars.) | The user: "don't ever use that ugly icon… the one you used before the 'you rated' text." | Convention (candidate: lint-ban the icon name). |
| 30 | **In-card confetti emits from the CENTRE — and diagnose before you change.** A `Confetti` clipped to a small card must use `origin="center"` (pieces start at the card's vertical middle and only rise **up**). `bottom` / `bottom-left` / `bottom-right` emit from the card's **bottom edge** — i.e. the footer strip where content like a rating star lives — so on device the animated pieces **sweep across that content** and it reads as missing/"glitchy" until they clear. Reserve `bottom` for a **full-screen** shower; if a card celebration must be bottom/corner, fire it at the **screen root** (decoupled from the card) instead. **Process:** don't guess the cause — the rating star *rendered correctly the whole time* (DOM: opacity 1, gathered); confetti was the only differentiator. The **headless preview can't render confetti motion** (rAF starved), so verify the **geometry** via DOM (confetti piece-Y vs the target's Y), not by eye. | The user: the 5★ "single star is glitchy, appears right before Book Again" — twice, and "don't do guesswork, find the REAL solution." | Convention (`BookingsScreen` 5★ burst; memory `in-card-confetti-emit-center`). |
| 31 | **A skeleton is a faithful GHOST of the real components — same radius, size, spacing, from the same tokens.** A loading placeholder must take its **corner radius, dimensions, padding and gaps from the actual elements it replaces**, not generic shapes: the card surface uses the card's `radius.default` + `size.12` padding + hairline border; a CTA ghost uses the button's `radius.md` (xs); a status pill uses the badge's `radius.sm`; the pro avatar is a `radius.default` rounded square (the `ProfessionalAvatar` squircle), not a circle; text-run ghosts use `radius.sm`. **Nothing is pill-shaped unless the real element is.** A soft fill (`border.default` @ `opacity.60` ≈ #EBEBEB) reads as a ghost, not a cartoon. This keeps the swap seamless (no layout shift) and on-brand. | The user: "our buttons are not pill shaped, why is the ghost UI not matching our styles, corner radius, card sizes, spacings?" and "too cartoonish and big." | Convention (`Skeleton` family + `BookingsScreen` `BookingCardSkeleton`; memory `skeleton-faithful-ghost`). |
| 32 | **Match the loading skeleton's COUNT to the content it loads into.** Render one placeholder per item the view is about to show (derive it from the active segment's/list's length when known), not a hardcoded number — otherwise the count is wrong (e.g. 3 ghosts → 2 real cards) and the swap adds/removes a row. Fall back to a small default only when the count genuinely can't be known (empty/first load). | The user: "if there are 2 cards in Upcoming, why do I see 3 cards in the ghost UI?" | Convention (`BookingsListSkeleton count` = active segment length). |
| 33 | **Button emphasis matches intent — `outline` is reserved for calm, low-emphasis / recovery actions; it is NOT a general style (for now).** Use `variant="outline"` ONLY for the single action in a deliberately-muted state — the **ErrorState `Retry`** and quiet empty-state prompts. Filled **`primary`** (solid brand) is for **high-intent conversion CTAs** (Book / Checkout / Apply, and forward empty-state nudges like "Add credit"). The DS **`secondary` is a gold fill** — a loud *accent*, NOT a "soft" option; never use it to calm an action down. Scope is intentionally narrow: don't reach for `outline` as a general secondary button elsewhere yet — revisit when more patterns need it. | The user, choosing outline for the ErrorState Retry: "this style is only for these kinda stuff (at least for now)." | Convention (`ErrorState` default `retryVariant='outline'`; memory `button-outline-for-calm-states`). |
| 34 | **A bespoke/composite field must MATCH the `Input` component — being tokenised is not enough.** Reuse-first (#1) extends to "looks like a DS field": when a control can't literally render `<Input>` (e.g. a phone field with a country chip in the same box, an OTP cell), it must still mirror `Input`'s tokens and behaviour — `radius.control` (12, not `radius.xl`), `borderWidth.default` (0.5), the dedicated **`input.*`** colour tokens (`input.border.default` / `.active` / `.error`, `input.bg.default`, `input.placeholder.color`) — and carry the **same states**, above all a **focus highlight** (border → `input.border.active`). Matching the Figma mock's raw look (e.g. radius 16) over the DS component is a divergence; reconcile to the component unless the user explicitly keeps the mock. | The user: "phone input field itself is consistent with our design system right?" — it matched the Figma but diverged from `Input` (radius 16 vs 12, 1px vs 0.5, no focus state, generic vs `input.*` tokens). | Convention (`OnboardingScreen` `PhoneField`; memory `field-matches-input-component`). |
| 35 | **A bottom CTA is keyboard-aware and navbar-aligned; every screen animation honours reduce-motion.** A primary bottom button **absolutely anchors** to the bottom so its position is identical across a flow's steps (not in normal flow, where taller content shifts it). At rest it sits at the **same inset as the floating navbar / checkout bar** (`safeArea.bottom`, 34). When the keyboard opens it **slides** (animated, synced to the keyboard event's `duration` + a `motion.easing` token) to a **small constant gap** (`space.md`) above the keyboard — never buried behind it, never a giant floating gap. Separately: **reduce-motion (`AccessibilityInfo.isReduceMotionEnabled`) must gate EVERY animation on a screen** — fades, slides, orbits, drives — not just some; when on, snap to end-state. | The user iterated the OTP CTA: "continue button should move above the keyboard" → "~34px above" → "closer + consistent across screens" → "default = navbar placement"; plus reduce-motion left uncovered on FadeIn/CTA. | Convention (`OnboardingScreen`; memory `keyboard-aware-cta` / `reduce-motion-covers-all`). |
| 36 | **Interactive surfaces glide — they never jump or fight.** Three faces of one rule, all reduce-motion-gated: (a) a **selection indicator slides** between states — animate its position *and* width to the measured target (`onLayout` per segment), don't toggle a per-item background (the SegmentedControl pill); (b) a **content-driven container animates its height change** — when a list filters and the sheet would resize, `LayoutAnimation.configureNext` (native; web no-op) so it eases instead of snapping (the country-picker BottomSheet); (c) a **directional drag locks the perpendicular scroll** — when a horizontal swipe claims the gesture, disable the parent `ScrollView` (`scrollEnabled={false}` on grant, restore on release/terminate) so the two axes don't compete (the Bookings carousel). | The user: the toggle "is just jumping … can we slide that pill?", the sheet "jumps … should move smoothly", and horizontal carousel swipe "also scrolls vertically … lock vertical scroll." | Convention (`SegmentedControl`, `BottomSheet`/`PageShell` `scrollEnabled`, `BookingsScreen`; memory `interactive-surfaces-glide`). |
| 37 | **Verify scroll/layout/z-order behaviour on the iOS Simulator before sharing — Storybook web is NOT proof.** RNW web rendering hides native-only bugs: RN `zIndex` on a screen's children can composite the screen *above* a sibling overlay (covered the app's bottom nav); programmatic `scrollTop` doesn't fire RNW's `Animated.event` `onScroll` (so a "working" web collapse can be inert on device); glass renders flat on web. For anything with scroll-driven motion, absolute/z-order layering, gestures, or glass: boot `xcrun simctl` + Expo Go and drive it. Prefer **paint order over `zIndex`** in screens; a scroll-collapsing hero needs **enough content height** (≥ a screen) or it can't fully collapse. | The user: "collapse is not working. did you test it? check it in a simulator… and page is covering the nav bar? these mistakes are unacceptable." (I'd only checked web.) | Convention (`WalletScreen`; memory `verify-rn-screens-on-simulator`). |
| 38 | **Every screen is built on `PageShell`, so its chrome is identical to every other screen — never re-implement it.** The screen **title is ALWAYS at the same coordinate**: in `PageShell`'s `bandContent`, `paddingTop: safeAreaTop + space.md`, `paddingHorizontal: space.md`, as `<Text variant="titleLarge">` (the Bookings title is the reference). **The title row MUST have a fixed `height: size.40`** — without it, `HStack align="center"` centers the title in a row whose height = the *tallest* child, so a taller trailing control (Bookings' `SegmentedControl` 36px) pushes the title down while a shorter one (Wallet's pill) doesn't → the two titles drift (Wallet was 4px higher). Fixed row height ⇒ title Y is independent of the trailing control (both now land at top=76 with `safeAreaTop=54`). The **content area ALWAYS has the rounded top** — it's `PageShell`'s content card (`radius.2xl` corners + the `cardShadow` seam over the band); a hand-rolled `ScrollView` gives a flat straight-edge top, which is wrong. Pinned vs collapsing is a `pinned` flag, but the title slot + rounded card are inherited either way. **Verify with a measurement** (compare the title's `getBoundingClientRect().top` across two screens) — don't eyeball it. **The content card's rounded top NEVER disappears mid-scroll.** Once the card scrolls under the header, `PageShell` pins a canvas strip with the card's own corners + shadow directly beneath it, so content passes behind a rounded edge exactly as it would inside a docked card. That strip rides the **collapse**, not the sticky row — a screen whose sticky row arrives much later (the salon funnel waits for its category grid to leave) or that has no sticky row at all would otherwise show a hard square edge for the whole gap between the two. **A media band docks; a title band scrolls.** When the band is a hero video or gradient, use `PageShell dockedCard`: the band is a FIXED layer that never moves, the content card rides up 1:1 with the finger until its rounded top meets the header and then **docks** there, and the content keeps scrolling inside it — Home's model. The default (band inside the scroller, sliding away behind a pinned header) is the iOS large-title pattern and is right only for a title band: media that slides off-screen reads as *the whole header scrolling*, which is not what a fixed header should ever do. | The user: "Booking page title and Wallet page title coordinates are inconsistent, fix that. IT SHOULD ALWAYS BE CONSISTENT" + "in our PageShell we have corner radius on pages; here the content side is a straight line at top. WHY?" (I'd bypassed `PageShell` and the title row had no fixed height.) | Convention (`PageShell`; `WalletScreen`/`BookingsScreen` title rows `height: size.40`, measured equal; memory `screens-built-on-pageshell`). |
| 39 | **A small caps label optically centers only when its `lineHeight` = its font size.** A short all-caps / digit label in a pill (`Badge`, chip, the gold "Save 35%") sits visually HIGH with the default variant leading (`labelXXSmall` is 9px font / **13px** line-height = 1.44×): the empty descender slack in the line box parks the glyph above optical centre **even though the box is padding-symmetric** (gapTop == gapBottom). `alignItems: center` centres the *box*, not the *ink*. Fix at the component: set the label's `lineHeight` to the variant's font size — **token-derived** `t.typography.labelXXSmall.fontSize`, never a raw `9` — so the line box hugs the caps and they truly centre. Verify gapTop == gapBottom **and** eyeball the glyph (the box being symmetric is not proof). **NATIVE CAVEAT (this fix is WEB-ONLY):** a `lineHeight` *smaller* than the font's natural leading renders the caps HIGH / clipped on **iOS** — so the tight-lineHeight trick centres on web but breaks on native, and it's the single most common "looks fine in Storybook, wrong on device" bug (#37). `Badge` therefore **platform-splits**: web keeps `lineHeight`=fontSize; native drops the override (natural line box, whose descender room re-balances the caps) + `includeFontPadding:false`. Any web-only text-metric fix MUST be re-checked on native. | The user, on the Wallet `Save 35%` badge: "this should be vertically centered." → then on the device: "these tags still have problem … why these got broken?" | Convention (`Badge` label `lineHeight`, `Platform.OS` split; memory `badge-label-optical-center`). |
| 40 | **The floating-nav "shrink on scroll" belongs on EVERY scrolling screen, not just home.** Drive it from the screen's scroll: `PageShell` exposes an `onScroll` prop (its **pinned** scroller previously had NO scroll listener at all — that was the bug) and the shared **`useNavShrink`** hook flips `compact` past `size.12` (same threshold as the home feed). ## Surface elevation

**`#FFF` (white) = raised; `#FBFAF7` = recessed.** That single rule drives every background:

| Level | Token | Light | Used for |
|---|---|---|---|
| Canvas (page base) | `background.canvas` | `#FBFAF7` | the screen / `PageShell` surface |
| Raised (cards on the page) | `background.surface` | `#FFFFFF` | cards, panels sitting on the canvas |
| Overlay (modals) | `background.surface-raised` | `#FFFFFF` | `BottomSheet` and other modal surfaces |
| Recessed (nested fills) | `background.secondary` | `#FBFAF7` | fills **inside** a white surface — cards inside a sheet, the close-circle, `NoteChip`, input fields |

So a card is **white on the canvas**, but **`#FBFAF7` when nested inside a white surface** (e.g. the same `PaymentMethodCard` is white on the checkout page, recessed inside the change-payment sheet — via its `recessed` prop). Don't hardcode page white; use `background.canvas` for screens so a screen can still opt into a white base later if a design calls for it. (Inverted 2026-06-19 from the old white-page model.)

## Proposals — the stakeholder sandbox (non-DS)

`packages/ui/src/proposals/` is a **sandbox for proposals from PMs / stakeholders** — ideas prototyped
*against* the system, not part of it. It has its own scoped `AGENTS.md`. The boundary, for any AI or
person working a proposal:

- **Write only inside `proposals/`.** Never touch `components/`, `screens/`, or `packages/tokens/` for
  a proposal, and never add or change a token.
- **Compose existing DS components** — tokens only; every rule above still applies.
- A proposal is a **suggestion, not a merge**: open a PR titled `Proposal: …` for the maintainers to
  review. `CODEOWNERS` (`*` → maintainers) already gates every merge, so nothing reaches the system
  without a design-team review — the sandbox just makes the boundary explicit and the diff easy to read.

The design team reviews proposals and rebuilds the approved ones properly under `components/`.

## Enforcing rules in code (the ladder)

Conventions are not meant to stay conventions forever — graduate them down this ladder as we go:

1. **Tokens / component defaults** — strongest; the rule is just *true* and can't be forgotten
   (e.g. `safeArea.bottom`, the default radius/spacing).
2. **Custom ESLint rules** — `tools/eslint-plugin-justlife/index.js` (wired in `eslint.config.mjs`).
   `no-raw-values` lives here; new rules (e.g. "a floating bottom bar must use `safeArea`",
   "no numeric spacing literal outside the scale") are added the same way and gated in CI.
3. **Tests** — unit + a11y today (Vitest + RNTL + jest-axe). Visual-regression (Chromatic /
   Storybook test-runner) is the path for shape/spacing drift like rule #6.
4. **CI gates** — `typecheck · lint · test · build` block merges that violate the above.

So: **yes, any convention here can become code-enforced.** When you implement a rule structurally,
move its row to `Enforced` and note the mechanism.
